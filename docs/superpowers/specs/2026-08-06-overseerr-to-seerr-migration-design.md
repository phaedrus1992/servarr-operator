# Overseerr → Seerr migration (issue #44)

## Context

Overseerr is unmaintained (upstream repo archived 2026-02-15); its team merged with Jellyseerr to
form **Seerr** (`seerr-team/seerr`, `ghcr.io/seerr-team/seerr`), the actively maintained successor.
This operator integrates Overseerr deeply — dedicated API client, CRD types, cross-app sync,
default image, charts, docs. This spec migrates that integration to Seerr while keeping existing
`ServarrApp`/`MediaStack` CRs functional across the upgrade.

The issue listed four open questions that had to be resolved before scoping the work. All four were
answered by checking out `seerr-team/seerr` and `sct/overseerr` to `~/git/reference/` and reading
source directly (not from docs/marketing), rather than assumed:

1. **API surface** — unchanged. Diffed `seerr/server/routes/settings/{sonarr,radarr}.ts` against
   overseerr's: same routes, same request/response shape, same `X-Api-Key` header auth. Only
   internal changes (async `settings.save()`, Sonarr v4 major-version branch). The `overseerr` crate
   already on crates.io works against a Seerr backend unmodified — no new Rust client needed.
2. **Data migration** — automatic, in-process. `seerr/server/lib/overseerrMerge.ts` detects an
   un-migrated Overseerr/Jellyseerr SQLite DB (`settings.main.mediaServerType` unset) and runs its
   schema migration and settings cleanup on first boot. The operator does no data transformation —
   it only needs to mount the *same* PVC that held Overseerr's `/config` data at the path the Seerr
   image expects.
3. **Image / port / deployment model** — `ghcr.io/seerr-team/seerr`, tag `v3.4.1` (latest stable),
   port `5055` (unchanged). Runs as a fixed `node` user, UID/GID `1000` (not configurable via
   PUID/PGID env vars, unlike the LinuxServer image it replaces). Config volume mounts at
   `/app/config`, not `/config`.
4. **CRD compatibility** — rename `AppType::Overseerr` → `AppType::Seerr` with a serde alias so
   existing CRs keep parsing; see below for the exact mechanism and its limits.

## Design

### 1. API client — rename only, no new dependency

- `crates/servarr-api/src/overseerr.rs` → `seerr.rs`. `OverseerrClient` → `SeerrClient`. Same
  underlying `overseerr = "0.1"` crate dependency (kept as-is in `Cargo.toml` — renaming or vendoring
  it would be pure churn since it already talks to Seerr's API correctly).
- `crates/servarr-api/src/lib.rs`: `pub mod seerr` + `pub use SeerrClient`.
- `crates/servarr-api/tests/api_tests.rs`: rename the wiremock-based client tests; assertions and
  fixtures stay the same since the wire format didn't change.

### 2. CRD types — rename with backward-compat alias

Rename throughout `crates/servarr-crds/src/v1alpha1/`:

| Old | New |
|---|---|
| `AppType::Overseerr` | `AppType::Seerr` |
| `OverseerrConfig` | `SeerrConfig` |
| `OverseerrServerDefaults` / `OverseerrServerDefaults4k` | `SeerrServerDefaults` / `SeerrServerDefaults4k` |
| `OverseerrSyncSpec` | `SeerrSyncSpec` |
| `overseerr_sync` field (spec.rs:114, media_stack.rs:150) | `seerr_sync` |
| `status.rs:77` `OVERSEERR_SYNC_READY` | `SEERR_SYNC_READY` |
| `OVERSEERR_FINALIZER` (controller.rs) | `SEERR_FINALIZER` |

**Backward compat for existing CRs:** existing CRs were written with `app: Overseerr` (confirmed
against `docs/examples/overseerr.yaml` — serde's default enum serialization is the bare Rust variant
name, not `as_str()`'s lowercase form, so the wire value is `Overseerr`, not `overseerr`). Add
`#[serde(alias = "Overseerr")]` on `AppType::Seerr`, and `#[serde(alias = "overseerrSync")]` on the
renamed `seerr_sync` field (the field itself is `#[serde(rename_all = "camelCase")]`d, so the old
wire name was `overseerrSync`). This makes Rust-side deserialization accept both spellings.

**Known limit — CRD schema, not Rust:** `charts/servarr-crds/templates/*.yaml` is generated by
`scripts/generate-crds.sh` (`cargo run -p servarr-operator -- crd`, via `schemars`/kube's
`CustomResourceExt`), never hand-edited. Whether `schemars` includes `#[serde(alias = ...)]` values
in the generated `enum:` list is unverified as of this writing — **verify this empirically as the
first implementation step** (generate the CRD, check if `Overseerr` is still a listed enum value
alongside `Seerr`). If schemars drops the alias from the schema, the Kubernetes API server will
reject a fresh `kubectl apply` of an old manifest still spelled `app: Overseerr` (a structural-schema
enum violation), even though already-persisted CRs with that value keep reconciling fine (K8s does
not re-validate stored objects against a new CRD schema on read, only on write). Document this
residual gap in the CHANGELOG rather than hand-patching the generated YAML — hand-editing generated
manifests is prohibited by project convention and gets overwritten on the next regen anyway.

### 3. Image defaults and deployment shape

`image-defaults.toml`: replace `[overseerr]` with:

```toml
[seerr]
repository = "ghcr.io/seerr-team/seerr"
tag = "v3.4.1"
port = 5055
security = "nonroot"
downloads = false
probe_path = "/api/v1/settings/public"
```

(`ghcr.io/...` is already precedented by `[maintainerr]`; `security = "nonroot"` is already
precedented by `[maintainerr]` and `[subgen]`.)

`crates/servarr-crds/src/v1alpha1/defaults.rs`, in `try_for_app`: add a `Seerr`-specific override
block immediately after the existing `Maintainerr` block (same shape, same justification pattern —
issue-numbered comment):

```rust
if matches!(app, super::AppType::Seerr) {
    // Issue #44: Seerr's image runs as a fixed `node` user (UID/GID 1000, not
    // configurable via PUID/PGID like the LinuxServer image it replaces), and
    // expects its config volume at /app/config, not /config.
    defaults.uid = 1000;
    defaults.gid = 1000;
    defaults.security = SecurityProfile::non_root(1000, 1000);
    let config_vol = defaults
        .persistence
        .volumes
        .iter_mut()
        .find(|v| v.name == "config")
        .ok_or_else(|| "Seerr defaults must have a 'config' volume".to_string())?;
    config_vol.mount_path = "/app/config".to_string();
}
```

No new abstraction: this is the same per-app override shape already used for Maintainerr's
`/opt/data` relocation (issue #131) and matches `SecurityProfile::non_root`'s existing `(user,
group)` parameters — `nonroot_base()` just happens to call it with the crate-wide `DEFAULT_UID`/
`DEFAULT_GID` (65534) today, and Seerr needs its own fixed values instead.

### 4. Existing-deployment upgrade path

Because Seerr self-migrates its own SQLite DB and settings on first boot (§Context, point 2), and
because the operator's `config` PVC is referenced by claim name — not by its in-pod mount path — the
upgrade path for an existing Overseerr `ServarrApp` is: **the user changes `app: Overseerr` (or
`Seerr`, once the CR is updated) on the existing CR**, and the operator's next reconcile produces a
new Deployment pointing the *same* PVC at `/app/config` in the new Seerr image. No volume snapshot,
no data copy, no init container. Seerr detects the inherited Overseerr DB and migrates it in-place on
first startup. Document this explicitly in `docs/backup-restore.md` (take a PVC snapshot first,
per existing convention for any risky operator-managed change) and in the CHANGELOG's `Changed`
entry.

### 5. Charts, docs, examples, smoke test

- `charts/servarr-operator/values.yaml`: update any `overseerr` default image reference.
- `docs/examples/overseerr.yaml` → `docs/examples/seerr.yaml` (`app: Seerr`); update
  `docs/examples/kitchen-sink.yaml`'s Overseerr entry.
- `docs/{configuration,examples,backup-restore,admin-credentials,installation,networking,
  nfs-volumes,troubleshooting}.md`: rename Overseerr references to Seerr; add a short migration
  note (mount-path change, fixed UID 1000, automatic DB migration) to `backup-restore.md`.
- `.github/smoke-test/manifests/overseerr.yaml` → `seerr.yaml`; update
  `.github/smoke-test/smoke-test.sh` references.
- `README.md`, `entities.json`: rename references.

### Testing

- Rename and keep the existing `crates/servarr-api/tests/api_tests.rs` Seerr client coverage
  (wiremock fixtures unchanged — API shape didn't move).
- `crates/servarr-operator/tests/reconcile_tests.rs`: rename `Overseerr`-specific cases; add a case
  asserting a CR with the legacy `app: Overseerr` spelling still reconciles (serde alias coverage).
- `crates/servarr-crds`: unit test that `AppType::Seerr` deserializes from both `"Seerr"` and
  `"Overseerr"`, and that `seerr_sync` deserializes from both `seerrSync` and `overseerrSync`.
- `AppDefaults::validate_all()`'s app list (defaults.rs:104-121): swap `AppType::Overseerr` for
  `AppType::Seerr`.
- Generate the CRD chart (`scripts/generate-crds.sh`) and manually inspect the `app` enum in the
  diff to confirm (or refute) whether `Overseerr` survived as an alias — this is the empirical check
  flagged in §2.

## Out of scope

- Seerr's new routes (`blocklist`, `watchlist`, `overrideRule`, `settings/metadata`) — the operator
  only ever used Sonarr/Radarr registration (`OverseerrSyncSpec`/`SeerrSyncSpec`) and the health
  probe; no new functionality is being wired up.
- A hard removal of the `Overseerr` alias — per the issue, end state is Seerr-only, but this PR
  keeps the alias for the transition window. Removing it is a future, separately-scoped issue once
  the CRD-schema-alias question (§2) is resolved and users have had a release to migrate.
